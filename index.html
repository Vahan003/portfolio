BUILDING DEADZONE

Developing a 3D multiplayer shooter that runs in the browser. Engineering case study and developer log. 001

Log 001 · Concept

Why this game had to run in a browser

I was always fascinated by games that run on the web without installers and huge download files. I know that in today's tech we can create a simulation and an entire world that fits in a browser tab, and I wanted to build something like that myself. DEADZONE is a competitive, third-person, multiplayer shooter* with a simulation inside it: bullets travel under gravity, walls stop them, players move through a shared world, and all of it runs in one tab.

* third-person shooter — a shooter where you control your own character and see the world from behind their shoulders.

The project grew from a simple client-side scene into a server* that simulates the game itself. Movement, bullets, and hit detection had to follow the same rules on both sides. This log follows how I got from one to the other.

* server — the official copy of the game running on a remote computer; in multiplayer it decides what really happens.

I knew what I wanted to create and I did not know how to create it. Starting a third person game from zero is hard. Writing the rendering myself on raw WebGL* was an option, and it would have meant building loaders, math, and scene management from scratch, which is inventing the wheel. Picking the right tech would deliver what I wanted, so that is what I did.

* WebGL — a browser technology for drawing 3D graphics on screen.

Log 002 · Stack

The libraries picked for the job

Three.js* does the rendering: scene graph, materials, shadow maps, loaders for FBX and OBJ. React Three Fiber* puts that scene inside React, so the world is written as components and React handles mounting and cleanup. Zustand* holds the game state, and its stores can be read from anywhere with getState()* during a frame without re-rendering anyone. WASM* covers the heavy math. The simulation core is defined in main.cpp, plain C++* compiled with Emscripten* through make.bat* into main_wasm.wasm, and both the browser and the server call the exported functions for collision, spread, recoil, and trajectory.

* Three.js — a JavaScript library for building 3D scenes in the browser.
* React Three Fiber — connects Three.js to React (the popular library for building web interfaces), so the 3D world is written as components.
* Zustand — a small library that keeps game state in one place so any part of the code can read it.
* getState() — a function that reads the current store value directly, without making React re-render anything.
* WASM (WebAssembly) — compiled code that runs at near-native speed inside the browser; .wasm files are its packages.
* C++ — a long-standing programming language; .cpp is its file type.
* Emscripten — a toolchain that compiles C++ into WASM so it can run in the browser.
* make.bat — a small Windows script that runs the compile step on double-click.

React and Next.js* wrap the app, Bun* runs the dev server and the game server, and ws* carries the network traffic. Every one of these was picked because it already solved a problem I would otherwise have had to solve myself.

* Next.js — a framework for building React web apps with fast loading.
* Bun — a fast program runner for JavaScript, similar to Node.js but quicker.
* ws — a small library that opens WebSockets: a live two-way connection between the web page and the server.

Log 003 · Architecture

The idea: one simulation shared by browser and server

The concept is short. A third-person shooter where the player runs through an industrial level, aims down sights*, fires projectiles that drop under gravity, and fights other players. Three.js renders what you see, React Three Fiber connects that world to the interface I already know how to write, and Zustand sits between them as the shared memory of the game.

* aim down sights (ADS) — lining the weapon's sights on a target; the camera zooms in.

WASM forms the numerical layer under everything. Positions, collision checks, recoil springs, bullet spread, all of it is computed by the same functions no matter which side calls them. That decision was made early, before the server existed, and everything after it depended on it. The client would one day become a view of a server simulation, so every rule had to live somewhere both sides could run. The shared folder exists because of that.

Log 004 · Client

Building the client before writing any server code

Everything was built on the client first. Enemies, hits, the level, all of it existed only in the browser and the server did not exist yet. Working this way let me decide how a frame should behave while everything could still change.

A couple of habits formed early, and both came from frames stuttering during aiming. Never call useState* inside a component that uses useFrame*. React state updates schedule renders, and inside the Canvas those renders compete with the frame loop* for time. A re-render landing in the middle of a frame shows up as a hitch while aiming. Components like Player, Bullets, and NetworkManager read and write through usePlayerStore.getState() and plain refs instead, and React only hears about the changes the HUD actually needs.

* useState — a React function that stores a value inside a component; every change schedules a re-render.
* useFrame — a React Three Fiber hook that runs code once per rendered frame.
* frame loop — the loop that updates and draws the game once per frame; any work in it competes with rendering.

Zustand subscriptions* also stayed out of the Canvas wherever possible. The canvas reads state many times per frame, and pushing a store update on each of those reads wakes subscriptions for data nobody watched. The stores belong to the UI, to the parts of the game that change slowly, and to handing a network snapshot into the world. Inside the frame loop, refs* and direct mutation do the work. The tab visibility hook switches the whole simulation off when the tab sits in the background, and every delta is clamped so coming back to the game cannot explode the physics.

* subscription — when a part of the UI asks to be updated only when a specific store value changes.
* ref — a plain variable that React does not re-render around; used to hold values that change every frame.

WASM was on the client from the first week. The mount path in DeadZoneGame.tsx loads the module and then initializes the helpers with the level data:

initClientColliders() uploads the level geometry into WASM memory, so a ray query* hits a block of floats* in linear memory* instead of walking JavaScript* objects.

* ray query — asking the world whether a ray (a straight line from one point to another) hits anything, and where.
* float — a decimal number (a number with fractions).
* linear memory — a flat, unbroken block of memory; WASM's world data lives there instead of as scattered objects.
* JavaScript — the standard programming language of web pages; the browser runs it natively.

Log 005 · Combat

Enemy hits on the client: weapons, recoil, billboard aim, hit registration

The first playable loop was local: enemies spawned, I shot at them, they went down. Every weapon is one entry in the table in weapons.ts, with damage, fireTime, dispersion, speed, recoilKick, adsSpreadMultiplier, and isFullAuto fields:

Recoil is computed as a spring*: a kick on fire, then a steady recovery after. It is stepped every tick*. Aim down sights swaps the field of view and scales the dispersion through one shared function, so both sides always agree on the numbers.

* spring — an imaginary elastic force that pulls something back to its resting position; used here so the gun kicks up on fire and then settles.
* tick — one fixed slice of game time (here 60 per second); the simulation advances in ticks, not in whatever frame rate the screen shows.

Shots are aimed by calculateBillboardBulletDirection* in camera.ts. It casts a ray from the center of the screen and tests it against a billboard* plane placed at each candidate, a quad that always faces the camera:

* calculateBillboardBulletDirection — the function that decides which way to fire so a shot aimed at a target actually lands on it.
* billboard — an invisible flat panel that always faces the camera, like a sign that turns to look at you; used here as the target surface for a shot.

The closest candidate plane decides the shot direction, and the bullet is aimed from the muzzle toward that plane. If the required bend away from the camera forward grows too large, the helper falls back to the camera direction, so a shot never snaps sideways. The candidate list in Player.tsx is built from the other players in the data stream, and the local enemies are tested the same way by segment checks in Bullets.tsx.

Log 006 · HUD

The HUD and menus

The HUD and menus use the DOM*, separate from the WebGL scene. Health, ammo, the crosshair, the death screen and the level menu are ordinary browser elements, updated only when the values they depend on change. A snapshot can update health or a shot can spend a round without requiring the interface to update on every frame.

* DOM — the document object model; the browser's tree of every element on the page, separate from the 3D graphics.

The interface carries status badges, a health bar with color thresholds, kill and death counters, ammo, weapon slots keyed to their bindings, and control hints generated from the same binding table* the input layer uses, so a hint can never advertise a key that does nothing. The edges of a match get their own overlays: a deploy screen whose click starts the match and takes pointer lock*, plus a death screen that counts down the server respawn timer. The level menu is a full-page overlay listing every level with a state badge; it disables itself while a level loads and surfaces load failures as text instead of leaving a dead screen.

* binding table — the list that maps each keyboard or mouse action to its key.
* pointer lock — a browser mode where the mouse cursor is hidden and movement becomes camera rotation, like in most shooters.

007

Log 007 · Audio

Audio

The sound layer is Web Audio* under the same budget rules as rendering. The context* lives for the session, created on demand and resumed on the first gesture* because browsers start it suspended. Buffers are decoded once and cached by URL; in-flight loads are deduplicated through a promise* map, so repeated requests share one decode; playback wraps the shared buffer in a fresh source node*, so the cost of a shot is nodes rather than a decode:

* Web Audio — the browser's API for generating and playing sound.
* context — the single audio engine object the page creates; once it is running, all sounds play through it.
* gesture — any interaction with the page, like a click or keypress; browsers require one before sound may start.
* promise — a JavaScript object that represents a value arriving later; here it remembers an in-flight file download so repeated requests share one decode.
* source node — a one-shot playback unit that takes a decoded sound and plays it.

Sounds are grouped by intent rather than by weapon: shots, hits, reloads, empty clicks, footsteps, deaths, kill confirmations, melee, explosions and voice lines. Each is a list to pick from at random so repeated shots do not sound stamped.

The pipeline is complete; the call sites* are not. The playback call is commented out at the place where a remote player muzzle flash is drawn, and the fired-this-tick flag that would trigger it already exists in the store. The missing piece is a handful of calls, not a system. The ambient bed, the low background layer of atmosphere, reuses the same discipline: tab visibility is already tracked and every per-frame system checks it, so ambience can gate on visibility and match state with the same flag.

* call sites — the spots in the code where a function is actually invoked to make a sound.

Log 008 · Ballistics

Frame tunneling, and the segment test that fixed it

Bullets move fast and frames cover enough time that the motion between them matters. For example, bullets move hundreds of meters per second, and in a single frame that is several meters of travel while an enemy body is about a meter wide. Checking only the bullet's new position every frame let shots walk straight through targets and cover.

* tunneling — when a fast object jumps from one side of a thin object to the other between frames, so the collision is never checked and it "passes through".

The fix was to stop checking positions and to check paths instead. Each frame keeps where the bullet was and where it is now, and the test becomes a ray stretched across the whole step, so it does not matter how far the bullet jumped:

* segment test — checking the line between two positions instead of just the second one, so nothing can be skipped over.

* raycastEnvironment — the shared function that checks a line segment against every wall and collider in the world.

Log 009 · Hit registration

sphereRayIntersection: the function behind body part hits

Walls use the environment raycast, but characters use a second function. sphereRayIntersection* in sphere-intersection.ts takes the same origin and direction as the environment test plus a sphere center, a radius, and a ray length, and returns the hit flag with the hit point:

* sphereRayIntersection — a shared math function that finds where a line hits a ball-shaped volume; used to separate head shots from body shots.

Each body part is one sphere from the BODY_PARTS table in body-parts.ts: head high on the body, torso at the chest, two legs lower down. The heights are feet-relative values, adjusted by getStanceHeight when the target crouches. The loop checks the spheres in table order and stops at the first hit, which is how a headshot is separated from a body shot before damage multipliers apply.

On the client the wrapper is LineOfSightHelpers.checkSphereHit*, in line-of-sight.ts. It converts the previous-position/current-position pair into start, normalized direction, and length, then forwards them:

* checkSphereHit — the client-side wrapper that prepares the previous and current positions and calls sphereRayIntersection.

A zero length segment returns NO_HIT immediately without calling into WASM. When WASM is absent the same math runs in sphereRayIntersectionFallback*, a quadratic solve* for the two parameters where the ray crosses the sphere, keeping only the values inside the segment length. The server calls the shared function directly per body part and keeps the closest hit by squared distance, then compares that distance against the environment hit distance so a wall between the muzzle and the target wins over the player behind it. Damage is scaled by the matching entry of BODY_PART_MULTIPLIERS (head highest, torso neutral, arms and legs lowest), and left and right legs are told apart by the sign of the horizontal offset between the player center and the hit point.

* sphereRayIntersectionFallback — the same math written in plain JavaScript, used when WASM is not available.
* quadratic solve — a fixed math formula (from the quadratic equation) that finds exactly where a line enters and exits a sphere.

010

Log 010 · Movement

Player movement, obstacle collision, and the follow camera

Movement is computed on a fixed step* on both machines by processPlayerMovement* in player-movement.ts. The keyboard turns into integer axes relative to the camera yaw, sprinting and crouching change the stance height, rolling is a timed request with a cooldown, and gravity integrates on the vertical velocity so falls stay predictable. Collision samples the body column* at a spacing defined in the game config, sweeps the direction through the WASM environment raycast, and slides the player along whatever it hits. The world bounds clamp the result so nobody walks off the map.

* processPlayerMovement — the shared function that computes where a player ends up this tick from input, sprint, crouch and roll.
* fixed step — simulating the game in equal tiny time slices (here 60 per second) so results do not depend on frame rate.
* body column — the vertical line of sample points through the character, checked against walls so head and feet are both solid.

The camera draws no attention to itself only while the distance to the player stays correct. It hangs behind the shoulder, and when a wall gets between it and the player the distance shortens, then returns once the wall is gone. CameraCollisionController* in camera-collision.ts casts a ray from the pivot toward the ideal camera position with a small radius around the lens, contracts almost instantly when something blocks it, and relaxes slowly when nothing does:

* CameraCollisionController — the component that keeps the camera from clipping through walls by pulling it in when something blocks it.

Every vector* the controller needs is allocated once at module scope, so a busy frame adds nothing for the collector*. The player model follows the interpolated position* computed from the previous and current server-known positions, and the shadow casting sun follows the same coordinates, so the shadow never lags behind the body.

* vector — a small set of numbers describing a position or direction in 3D space.
* collector — the garbage collector, the browser's cleanup system that reclaims memory that is no longer used.
* interpolated position — a smooth position between two known ones (previous and current), used so movement looks fluid instead of jumping.

raycastEnvironment() normalizes the direction inside and asks WASM whether anything crosses the segment. Body parts use the same shape of call through sphereRayIntersection. Obstacles came in the same pass: colliders* are extracted from the level objects once with extractCompositeColliders() and uploaded with uploadCollidersToWasm(), so every segment query and every movement sweep reads the same copy of the world. Enemies and walls finally sat in one physical world.

* collider — an invisible shape that blocks movement and shots; the physics twin of a visible object.

Log 011 · Projectiles

Bullet drop, batched environment queries, and spent rounds

Bullets obey gravity, so each shot follows the same downward arc defined by the trajectory* helper instead of flying straight forever. The server integrates the arc in updateProjectiles()*, and the following lines match the calculations the client runs through CombatHelpers.projectileTrajectorySync:

* trajectory — the curved path a bullet follows under gravity; here, the arc computed in advance for every shot.
* updateProjectiles — the server-side step that moves every active bullet along its arc each tick.

The projectile pool is a fixed set of bullet records reused instead of created and thrown away. Spawning overwrites the next slot in a round-robin* cycle, so when the pool is full the oldest bullet in flight dies quietly and its slot is reused:

* round-robin — taking slots one after another in a circle, looping back to the start when you reach the end.

Every bullet casting against the whole level on every frame becomes measurable cost once many bullets are active, so the queries moved into one batched WASM call. batchBulletsVsEnvironment* takes every ray at once and writes back the hit flag, the distance, the hit point, and the surface normal for each of them:

* batchBulletsVsEnvironment — a single WASM call that traces all active bullets against the world at once, instead of one call per bullet.

* _malloc / _free — functions that reserve and return memory inside WASM.
* HEAPF32 — WASM's raw memory viewed as a list of 32-bit floats.

The buffers exist only for the duration of the call, so many active bullets add no long-lived garbage for the collector to collect later. Cleanup is the other half: a bullet that hits something or runs out of life deactivates instead of being deleted, and its tracer mesh is reused. Impacts record their point into a ring buffer*, which the ballistics overlay and the server comparison read later.

* ring buffer — a fixed-size circular list; when it is full the oldest entries are overwritten, so it never grows.

Log 012 · Rendering

Level layout, lighting, shadows, and the occlusion shader

The environment is assembled from OBJ* pieces under models and laid out by the level data in data, a catalog of numbered versions where currentLevelKey picks the active one. Every object that blocks shots declares itself as a collider, and that one declaration feeds rendering, the barrier* list, and the collider upload, so the picture and the physics describe the same world.

* OBJ — a common 3D model file format; the level is built from many small parts.
* barrier — a wall-like object that blocks bullets; the shared list of all barriers keeps physics and visuals in sync.

Lighting took real thought. One directional light casts the shadows, and its follow target tracks the player position, so the shadow map* covers the area around the character. The follow target is quantized to the texel* grid of the shadow map, which keeps the shadow from crawling while the camera moves. Around that sit an ambient light, a hemisphere light for sky and ground color, a fog matched to the sky color, and a procedural sky baked into a PMREM texture* that gives the materials something to reflect.

* shadow map — a small image that records which parts of the scene are in shadow; the shadow camera draws it every frame.
* texel — a single pixel inside a texture image.
* PMREM texture — a 360° environment image baked into a cube so materials can reflect the sky realistically.

Ambient occlusion was the piece I rewrote by hand. The stock SSAO* blur mixes foreground occlusion into unrelated background pixels, so the blur shader* inside DeadZoneGame.tsx became a bilateral version that compares depth and normals between samples and only lets nearby, similarly oriented surfaces influence each other:

* SSAO (screen-space ambient occlusion) — a trick that darkens the contact between surfaces so they look attached; the stock version blurs too much, so it was rewritten.
* shader — a small program that runs on the graphics card to draw every pixel (here, the one that darkens contact edges); written in GLSL.

The range check runs in view space* rather than normalized depth, so a wall far behind the player stops catching a dark silhouette from someone standing in front. The pass also refreshes the projection matrix* every frame, because aiming down sights changes the field of view constantly and SSAO only refreshes its projection on resize.

* view space — coordinates measured from the camera; normalized depth is the compressed distance value WebGL uses for every pixel.
* projection matrix — the math that flattens a 3D scene onto the screen; it changes whenever the field of view changes.

Log 013 · Animation

Character animations and loading clips without skins

Characters come from Mixamo* style FBX* files, and the first version carried a full skinned mesh* in every animation file, which is a lot of duplicated geometry in memory for what is really bone motion. The fix showed up in the filenames: the clips were re-exported without skin, so the models directory now holds files like Walk_forward_without_skin.fbx, Run_left_without_skin.fbx, and Death_from_the_front_without_skin.fbx next to the skinned idle the character is cloned from.

* Mixamo — a catalog of ready-made character animations (walk, run, death) that can be applied to any model.
* FBX — a 3D file format that carries models, bones and animation together.
* skinned mesh — a model whose surface is bound to a skeleton of bones so it can bend and move.

The base model comes from Idle.fbx and is cloned once with SkeletonUtils.clone, then every clip* attaches to that single skeleton through one AnimationMixer*. Clips get adjusted in code as well. Root motion* is stripped from position tracks* so an animation plays without dragging the character across the map:

* clip — a self-contained piece of character animation (walk, run, death).
* AnimationMixer — the object that blends and plays animation clips on one model.
* root motion — the movement baked into an animation (like walking in place); stripped out so the animation does not drag the character across the map.
* track — one piece of animation data, e.g. how a bone's position changes over time.

The dive roll arrives once and becomes backward, left, and right versions by premultiplying a quaternion* onto the hips track. The core set loads with the model, and the optional strafe and hit reaction clips stream in later against a promise cache, so a slow file never blocks the player from appearing.

* quaternion — a math object that describes a 3D rotation without the wobble of angles; used to mirror the roll into left and right versions.

Log 014 · Server

The server: WebSocket, binary packets, tick loop, and WASM

Multiplayer meant moving the truth somewhere both machines could see it. The transport is WebSocket and every game packet* is binary*. An input packet is packed into a fixed layout* where each field only gets the bytes it needs:

* packet — one chunk of data sent over the network, with a fixed layout.
* binary — data as raw bytes rather than text; smaller and faster to send.
* fixed layout — every piece of data always sits at the same byte position, so both sides can read it without guessing.

Snapshots* come back the same way: a small header plus a fixed record per player, and each client's snapshot carries that client's own last processed input sequence*, which reconciliation later compares against. The server runs under Bun through dev-server.ts, and its tick loop accumulates time and caps catch-up steps so a hiccup cannot spiral into minutes of simulated time:

* snapshot — a frozen picture of the whole game state, sent to every client so they all see the same world.
* sequence — a unique counter given to every input; it eventually wraps (rolls over from max back to zero), and comparisons handle that.

React and Zustand stay out of the server process entirely. The simulation holds plain maps of players, inputs, and bullets, and the client NetworkManager owns the socket, builds input packets, sends them, and applies snapshots. WASM went to the server as well through loadWasmServer(), with the level barriers and colliders uploaded into its memory during initialization; if the module fails to load, the server logs a warning and falls back to the pure JavaScript path.

Log 015 · Network

Quantization: fitting game state into small integers

Every float that crosses the network is quantized* first, and there are two concrete reasons. The first is size: a fixed layout lets the serializer write bytes at known offsets instead of formatting numbers. The second is agreement: both sides round through the same function, so client and server land on the same value instead of drifting apart in the last decimal places.

* quantized — rounded into a smaller set of values so it fits in fewer bytes; both sides round with the same rule, so they always agree.

Angles ride as sixteen bit values over a full circle. The aim direction and the settled recoil are signed sixteen bit vectors scaled from their natural ranges. Movement axes are two signed bytes, the button mask* is one byte, the weapon id is one byte, and the frame delta goes out as integer milliseconds clamped to a small range, which the server divides back into seconds when it parses the packet. Positions in snapshots map into an unsigned sixteen bit range over the world bounds, health takes a byte, and the respawn timer is stored in tenths of a second.

* bitmask — several on/off flags packed into the bits of one byte (each bit = one action).

Sequence numbers deserve their own note because they wrap: the counter is unsigned and every comparison goes through the wrap-aware helpers in sequence.ts, so the fire interval check still works when the counter rolls over instead of silently locking the trigger.

Log 016 · Workers

Web workers: parsing snapshots off the main thread

A snapshot arrives many times a second, and parsing binary on the main thread would take time away from rendering. WebSocketClient therefore owns three workers*, created with new Worker(new URL(...), { type: "module" }), and the incoming buffer is handed over as a transferable* so the main thread does not copy it around:

* Web Worker — a background thread that does work without blocking the main page; here, workers parse snapshots.
* transferable — an object whose ownership is handed over to another thread instead of being copied, saving time and memory.

The network worker deserializes the snapshot and writes every player into one shared Float32Array* with a fixed stride*: active flag, position, yaw, pitch, actions, health. Back on the main thread playerDataStream.readWorkerData() splits that buffer into typed arrays, so rendering reads flat memory instead of building a fresh object per player per frame:

* Float32Array — a typed array: a flat list of 32-bit floats, used here as one shared block of player data.
* stride — the number of values between two consecutive players in that flat list.

The game worker deserializes the same packet into a SnapshotPacket and posts it back, where UpdateGameFromSnapshot takes the local player id, health, respawn state, the throttled match clock, and reconciliation. The stats worker parses the small JSON messages carrying scoreboard numbers, so JSON.parse* never lands on the main thread either. One field is deliberately excluded from the worker stream: the comment in player-data-stream.ts notes that recoil belongs to the main thread snapshot path.

* JSON.parse — turns text (JSON, a compact data format) into values JavaScript can use.

Log 017 · Remote players

Rendering other players on the client

OtherPlayers renders each remote player through BasePlayer, which reuses the model, the material cache*, and the animation hook of the local character, with team accents painted into a small canvas texture so the sides read apart at a glance. Remote state arrives through the worker typed arrays and is interpolated between the previous and current position with the same interpolationAlpha the local player uses, which is why remote characters move smoothly instead of teleporting. The HUD, the scoreboard, and the debug overlay read the same stores afterward.

* material — the recipe for how a surface looks (color, roughness, reflection); shared across characters to avoid duplicates.

Log 018 · Prediction

Reconciliation: client position against server position

The client predicts its own movement, fires on the frame it wants to fire, and shows the result immediately. Any other approach feels unresponsive. Every tick NetworkManager reserves a sequence number, packs the input, keeps a copy in pendingInputs, sends it, and records where the player ended up in posHistory:

pendingInputs is the queue of unacknowledged inputs, and posHistory records where the player ended up at each sequence. Both queues are bounded, and when they overflow the oldest entry is dropped while frameActionAudit.pendingTrim logs a warning in development builds.

Every snapshot carries lastProcessedInput, the highest sequence the server has handled. handleReconciliation in update-game-from-snapshot.ts finds the position the client had predicted at that sequence, and compares it with the position the server reported:

The comparison runs against the historical position at the acknowledged sequence, never against the latest predicted position, because the client advances several ticks ahead of the server and comparing against its current state would report an error on every single snapshot. The squared error* measures the gap between the predicted and reported position, and RECONCILE_THRESHOLD_SQ is the cutoff, so a gap under half a meter is left alone. When the squared error crosses the threshold the player snaps to the server position, the inputs still waiting for acknowledgement are walked from that corrected state, and frameActionAudit.reconcile records the size of the correction and how many inputs were involved. If the history entry for that sequence is already gone, posHistoryFallback logs it instead of comparing against the wrong position.

* squared error — the gap between two positions multiplied by itself; a common way to measure distance without square roots.

019

Log 019 · Trust

Anticheat: what the server decides for itself

If the client could choose the damage, a modified client could choose anything, so the server treats every packet as a claim and checks it against its own state. Button masks are sanitized the moment an input arrives. sanitizePlayerActions masks the raw value to known bits, strips the flags only the server may set, and enforces the stance rules so impossible combinations never enter the simulation:

The fired-this-tick and reload flags are server only, so a client cannot forge them through the button bitmask. The weapon id in the packet is checked against the weapon table before use. Fire rate comes from the gap between sequence numbers rather than from a timer the client controls, and semi automatic weapons mirror the client's edge detection*, so one press means one shot on both machines.

* edge detection — noticing that a key went from not-pressed to pressed (or back), so one press means one shot on both machines.

The muzzle position never crosses the network. Both sides compute it from feet position, aim direction, and crouch flag through computeMuzzleSync. The recoil inside the packet is kept in its own fields for cross checking only; the server steps its own recoil spring and never takes aim from the client's copy. Health, damage, kills, and respawns are decided on the server, and the client hit code says the same thing in its own comment: visual hit only, damage is server authoritative*. The health station resupplies on the server's clock as well.

* server authoritative — the server's copy of the truth wins; the client may guess, but the server decides what really happened.

frameActionAudit adds a development layer on top of that: it logs the sequence and seed of every shot the client predicted and every shot the server executed, so a mismatch in spread or timing appears in the console before it turns into an inconsistency nobody can explain.

020

Log 020 · Determinism

The same random spread on both machines, using mulberry32

Shot spread is random, and two machines given the same request have to reach the same answer or they will disagree about where the bullet went. mulberry32* in mulberry32.ts is the generator used for that:

* mulberry32 — a small function (a "generator") that turns one seed into a stream of random-looking numbers; the same seed always gives the same stream.

The seed* is the input sequence number. NetworkManager picks the sequence when it builds the packet on the client, and the server reads that same sequence out of the received packet. Both feed it into bulletSpreadSync:

* seed — one number that fully determines a random-looking stream; both machines use the same seed, so they get the same "randomness".

Pellets add their own index to the seed, so every pellet of a shotgun blast lines up on both sides. The C++ module declares its random state at namespace scope* precisely so client, server, and WASM produce the same numbers, and this is where the earlier decision to share every function paid off: CombatHelpers.bulletSpreadSync, the recoil spring, computeMuzzleSync, and the trajectory helper all exist in shared code, and one dispersion model has two callers.

* namespace scope — a place in the code outside any function, where values are shared by everything in that file.

021

Log 021 · Core

Moving the client systems into the server simulation

The last big stretch folded the two halves together. Local enemies stepped aside for server driven players, and the environment that used to exist only in the browser now lives in server memory as barriers, colliders, and world bounds.

Everything that decides an outcome moved into utils and is called from both sides: processPlayerMovement for walking, sprinting, crouching, and rolling, raycastEnvironment and the sphere intersection for hits, computeMuzzleSync for spawn points, the recoil spring functions, the dispersion model, and the trajectory helper. The server replays each input through that code, spawns the authoritative bullet on the same frame with the same direction, integrates the same arc, batches its rays against the same colliders, and applies the body part multipliers from the shared config. The left leg and right leg call still comes from the sign of the hit offset, exactly as the client does it. The server holds the truth, the client holds the prediction, and they settle their differences on every snapshot.

022

Log 022 · Tooling

A separate viewer for the server simulation and desync markers

Desync* is hard to spot from inside the game. You can play for an hour feeling that something is slightly off and never pin down what it is.

* desync — when the client's picture of the game drifts from the server's truth; hard to spot from inside the game.

So the server got a viewer of its own process. debug-server.ts starts an isolated HTTP* server with its own WebSocket and serves a standalone page from server-visual, sharing nothing with the game socket. It only reads the simulation through getDebugSnapshot(), which allocates a plain copy of the state and never hands out a live object, so the viewer cannot disturb a match. The feed carries player positions, angles, crouch flags, health, bullets with their origin and direction, and a ring buffer of recent hit points, and a key in that window clears the markers.

* HTTP — the standard protocol for loading web pages; here it serves the viewer page separately from the game socket.

The client records its impacts too, from environment hits and body hits alike, and the DebugBallistics overlay draws every trajectory ray and recent hit marker through two shared draw calls on preallocated buffers, whatever the number of live traces. Checking where the client placed an impact against where the server recorded one makes the disagreement obvious within seconds, and it caught problems that reading code would have missed.

023

Log 023 · Performance

Performance work and the tools that made it possible

A list of what actually mattered, with no ranking implied. Store subscriptions stay out of the frame loop, and getState() reads happen without subscribing. Scratch vectors for camera, collision, and combat work are allocated ahead of time, so the garbage collector runs no cleanup passes for them when many bullets are active. Bullet tracer meshes come from a pool, and the debug overlay draws every ray through a single buffer. Animation clips share one skeleton. Player data crosses threads as typed arrays with a fixed stride. Bullet rays go to WASM in one batched call. Snapshots are binary and quantized before they leave the server. The tab visibility hook pauses the simulation in the background, and every delta is clamped so returning to the game cannot explode the physics.

Three.js gives the shadow and post processing* control to make all of that look right at the same time. React and Zustand keep the interface consistent without adding work to the hot path*. WASM keeps the expensive loops close to the metal while shipping as a single file the browser caches. Bun keeps server restarts fast enough that restarting it many times a day during debugging is cheap. Each of those choices bought control, and the frame timeline monitor* in the corner of the screen shows the result.

* post processing — extra image effects applied to the finished frame (like a film grade).
* hot path — the code that runs every single frame; anything slow there costs the whole game.
* frame timeline monitor — a small HUD chart showing how long each part of a frame took, so hitches are visible as spikes.

024

Log 024 · Lessons

What we learned

01

Starting a project like this from zero teaches as much about decisions as about code. Locking the stack in early and sticking with it mattered more than any single algorithm. Three.js, React Three Fiber, Zustand, WASM each earned their place, and the time saved went into the parts that make the game itself.

02

Sharing code between client and server turned out to be the most valuable structural decision in the project. A function that exists once and runs in both places removes a whole category of bugs, and the seeded spread only works because of it.

03

Writing the game before the server was the right order. I learned what the simulation had to be while I could still change it, and by the time the server arrived the shape of the thing was already clear.

04

Debug tooling belongs with the game itself. The standalone viewer, the hit point ring buffers, the frame action audit, and the FPS timeline caught more issues than careful reading ever did. The tools that show what the machine actually did were worth more than reading the code again.
